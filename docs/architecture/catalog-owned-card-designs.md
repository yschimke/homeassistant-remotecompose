# Website-owned card designs

This is a staged ownership change. It does not turn historical design plans into evidence that
existing cards already have authoritative editable source.

## Current ownership and the cutover seam

`card-designs:generateCardDesigns` still captures converter code into the bundled library. Its
`HaCardsSeed.source` is an approximate reconstruction, not that library's editable source.
`UserDesignStore` stores personal RC variants and a builder revision reference, without retaining
source history. Published component catalogs and cached builder templates are a different layer:
they describe the editor's vocabulary/starting documents, not the HA runtime design library.

The published-catalog worker's server #1745, builder #956 and private config #5 cover rooted offline
editor creation and removal of ignored ownership settings. Reuse their released artifacts and
production gates. Do not replace them, restore implicit seed factories, or assume that their offline
harness proves an HA card is equivalent to its UID reconstruction.

The website publication store overlays the bundled library by runtime `DesignKey`. For those keys,
`publications.json` retains the exact UID, compiler release, generated artifact digest, example and
publisher at every revision. `/api/designs/<id>/source.uid` returns those exact stored documents.
For every other key the existing library remains authoritative until an equivalence review passes.
IKEA (#912) and the ten family designs (#913, now merged) remain converter-owned during that review. Their style
IDs are discovered from publications; there is no new parallel implementation of their artwork.

## Admin workflow

Mount `CATALOG_DESIGNS_DIR` on durable storage outside the deployment image. Mount a JSON
`CATALOG_SETTINGS_FILE` containing `{"adminActors":["github:your-login"]}` read-only. Empty policy
grants nobody publication rights. On the shared host, authenticate through the existing builder
session/identity endpoint; ordinary editor rights alone do not grant publication. The separate HA
GitHub session also works when the HA server runs independently.

1. Open `/studio/catalog` while signed in. Create a design in the existing builder, import a UID,
   or open a retained source as a new editor draft. Opening a source always creates a new builder
   ID and shares it with the requesting admin; it never replaces another person's draft.
2. Load the committed source or import the UID. Choose a stable publication ID, the supported
   card contract ID, runtime key, and expected publication revision (zero for a new design).
   A new style/variant can reuse a supported shape without an app/server deployment.
3. Validate and preview. The source must have a resolved catalog revision. Native capture asks the
   catalog's real compiler to capture that exact supplied document; it does not synthesize a
   converter or flatten unknown catalog components into lookalikes. The generic native-capture
   endpoint validates source export and catalog pins through the existing service before compiling.
4. Play the generated bytes in the existing RC browser player, resize the frame, push test values
   without regenerating, and inspect simulated host actions. Publish only after reviewing them.
5. Publication recompiles twice, requires identical output, checks target operations, live binding
   names/types and host action payloads, then atomically commits the UID and content-addressed RC.
   A stale expected revision returns 409 even when the compiler finished after another publication.
6. To recover, select an earlier retained revision and publish its source against the current
   revision. Recovery adds history; it never rewrites published history or a builder draft.

Some existing catalog protocols use `nativeRuntimeId: "candidate"` as their compatibility marker.
Retain that declared value and record the exact server/compiler release separately. Reproduction
requires that compiler release and the source's catalog revision, not whatever renderer is latest.
A compiler deployment changing during generation or nondeterministic bytes prevents publication.

Current gates deliberately refuse external asset bindings, expression-generated host action payloads,
and widget native capture without a separate target-profile contract. They must gain asset bundles
or semantic equivalence validators before those capabilities migrate. Refusal leaves the old design
serving; it is not a migration success. Name/type/action validation also does not prove visual parity,
responsive layout, hit-region reachability, or every state-driven color/reading. Those need real
player tests and responsive/state matrices before a converter-owned key is replaced.

## Discovery and offline behavior

The public manifest, browser, schema and card resolver use the same live publication overlay.
`/api/designs/catalog/styles` lists runtime style IDs without a code chooser update. Both shared
browser dashboard hosts refresh the list and RC bytes while open. Android's native design choice
accepts an independent catalog style ID, so a newly published style need not become a Kotlin enum.
Catalog mode selection does not alter the bundled fallback style.

Browser, desktop and shared Android playback cache verified public artifacts under a versioned
namespace. Cache keys use anonymous card shapes/style/mode, not entity credentials. Failed refresh,
storage quota errors and malformed cached bytes keep last-good playback or the built-in card. The
native Android repository continues to use its disk manifest/blob cache and local converter fallback.
These caches do not make an uncached app shell available offline. Rooted editor shell/template
creation remains gated on the published-catalog worker's compatible releases and cold-offline test.
Do not retire bundled designs or offline editor seeds on the strength of a warm playback test.

## Repository snapshots

`catalog-design-backup.yml` runs daily or manually. `scripts/import-catalog-designs.py` reads only
public published history, verifies RC sizes/digests, and writes deterministic UID/RC/metadata files to
`catalog-backup/`. It rejects serial rollback, lost/rewritten history, unsafe paths and unsupported
unbundled assets. It records compiler releases and complete catalog pins; a second identical import
changes no files. It never uploads to the website and has no deployment/operator credential.

The workflow reuses `agent/catalog-backup` without force pushes and opens a draft review PR. GitHub
permissions are limited to repository contents and PR creation; public website reads require no
credential. Drafts avoid the existing scheduled merger. Repository backup merge order never selects
website publication order. Do not feed these files into a website upload or design-generation job.
The runtime volume and builder drafts/ACLs also need private operational backups and a restore drill;
public snapshots contain neither unpublished work nor access-control state.

## Release and rollout order

1. Release [compose-ai-tools #6085](https://github.com/yschimke/compose-ai-tools/pull/6085),
   then pin this repository's producer to that actual release and publish a corrected HA authoring
   catalog before changing ownership. Do not leave the producer pinned to the IR-pruning release. Its discovery must include
   `HaCardTemplate` / `HaCardUberTheme` as callable library components, and its native bundle must
   retain those callable classes even when stickers already have baked IR. The published 2.66.0
   bundle prunes the sticker/component facade; successful sticker replay does not prove native
   authoring works. Keep the component catalog and bundle from the same producer run/revision.
2. Release compose-ui-builder #957 (supplied-document stable Compose source export), then update
   compose-preview-server #1747 to that real released version and release its native capture API.
   Do not ship the server endpoint against the old builder floor or treat a local composite build
   as a published dependency. Review/release the reusable server's native document capture API. It uses the existing native
   catalog compiler and RC capture terminal; it does not enable the unrelated experimental lowerer.
   Verify the served HA catalog has an Android capture bundle with matching component/runtime
   versions, valid RC capture support, named bindings and host actions.
3. Integrate the published-catalog worker's compatible builder/server releases. Verify fresh-tab
   offline editor creation in production before retiring any chooser/seed compatibility.
4. Release the HA image with the website store, validator, UI and discovery/cache changes. Preserve
   its bundled library. Deploy the private deployment repository's durable-volume/admin-policy wiring
   using the active writer's reviewed handoff procedure. The private deployment repo remains staged
   until its own cutover gates pass; do not move HA deployment ownership back into the reusable server.
5. Capture before/after evidence: an authenticated admin creates a previously unknown style through
   the website, validates RC playback at small/large widths and changing values/actions, publishes,
   and a second client discovers/plays it without restarting services or rebuilding apps.
6. Run the backup importer twice and test recovering a retained revision. Replace the HA container
   and verify source history survives. Warm playback/editor caches, disable network, open fresh tabs,
   and verify creation/playback plus bundled fallback. Record exact released versions and image digests.
7. Migrate existing designs by shape/style/mode/surface. Compare source-generated RC against shipped
   bytes over live data/actions, responsive frames and target profiles. Include IKEA and all ten
   incoming families. Keep an explicit pending entry for every unsupported shape/capability.
8. Only after those comparisons, offline checks and live cutover pass, retire the corresponding
   converter ownership/chooser entries. Do not remove an entire family because one frame matched.

No PR merge is authorized by this runbook. Local JVM/HTTP/browser evidence and deployed behavior must
be recorded separately. A mock compiler tests orchestration; it cannot establish UID-to-RC fidelity.
